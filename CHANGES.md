# SSD300 — Migration from Pascal VOC to DIOR

This document records every code change made to adapt the original SSD300
codebase (built for Pascal VOC) to train and evaluate on the DIOR satellite
imagery dataset across five data-efficiency splits.

---

## Project Goal

We are running a **data efficiency study** comparing two object detectors on the
DIOR dataset (20-class satellite imagery):

- **YOLOv8n** — already trained and results saved in `Results/YOLO Results/`
- **SSD300** — being adapted and trained here

Both models are trained five times, each time with a different fraction of the
training data (5%, 25%, 50%, 75%, 100%), using the same stratified nested
index files from `Python_datareader/`. The result is a learning curve (mAP vs.
training set size) that lets us compare the two architectures.

### 1. `utils.py` — Label Map

#### What it does

`utils.py` defines the global label map used by every other file. Every class
name maps to an integer ID. The SSD convention is:

```
0           → background  (no object)
1 … n       → real classes
```

#### Before (Pascal VOC, 20 classes)

```python
# Label map
```

### 2. `datasets.py` — Dataset Class

#### What it does

The dataset class is responsible for:
1. Finding image and annotation files on disk
2. Loading and parsing them
3. Applying transforms (resize, normalize, augmentation)
4. Returning `(image, boxes, labels, difficulties)` per sample

#### Before (Pascal VOC — `PascalVOCDataset`)

The original class relied on **two JSON files** generated by
`create_data_lists.py` as a preprocessing step:

- `TRAIN_images.json` — list of image paths
- `TRAIN_objects.json` — list of `{boxes, labels, difficulties}` dicts

```python
class PascalVOCDataset(Dataset):
    def __init__(self, data_folder, split, keep_difficult=False):
        self.split = split.upper()  # 'TRAIN' or 'TEST'
        self.data_folder = data_folder
        self.keep_difficult = keep_difficult

        # Requires pre-generated JSON files
        with open(os.path.join(data_folder, self.split + '_images.json'), 'r') as j:
            self.images = json.load(j)
        with open(os.path.join(data_folder, self.split + '_objects.json'), 'r') as j:
            self.objects = json.load(j)

    def __getitem__(self, i):
        image = Image.open(self.images[i], mode='r').convert('RGB')

        objects = self.objects[i]
        boxes       = torch.FloatTensor(objects['boxes'])
        labels      = torch.LongTensor(objects['labels'])   # already 1-indexed
        difficulties = torch.ByteTensor(objects['difficulties'])  # 0 or 1 per object

        # Drop difficult objects if not needed
        if not self.keep_difficult:
            boxes       = boxes[1 - difficulties]
            labels      = labels[1 - difficulties]
            difficulties = difficulties[1 - difficulties]

        image, boxes, labels, difficulties = transform(
            image, boxes, labels, difficulties, split=self.split
        )
        return image, boxes, labels, difficulties
```

**Problems with this approach for DIOR:**
- Requires running `create_data_lists.py` first to generate JSON files
- JSON files would need regenerating every time you switch splits (5%, 25%, etc.)
- Pascal VOC has a `<difficult>` flag in annotations; DIOR does not
- Pascal VOC labels are pre-shifted to 1-indexed in the JSON; DIOR returns 0-indexed

#### After (DIOR — `DIORDataset`)

The new class reads XML annotations directly — no preprocessing step needed.
It accepts a `split_file` parameter (a `.npy` index file) to select any of
the five data-efficiency subsets.

```python
class DIORDataset(Dataset):
    def __init__(self, data_dir, split='trainval', split_file=None, split_name='TRAIN'):
        # split:      'trainval' or 'test' — which image folder to read from
        # split_file: path to split_005_indices.npy etc. (None = full split)
        # split_name: 'TRAIN' or 'TEST'  — controls whether augmentation is applied

        img_dir  = os.path.join(data_dir, f'JPEGImages-{split}')
        ann_dir  = os.path.join(data_dir, 'Annotations', 'Horizontal Bounding Boxes')
        main_dir = os.path.join(data_dir, 'Main')

        # Read all image IDs from train.txt + val.txt (or test.txt)
        id_files = ['train.txt', 'val.txt'] if split == 'trainval' else ['test.txt']
        all_ids = []
        for fname in id_files:
            with open(os.path.join(main_dir, fname)) as f:
                all_ids.extend(line.strip() for line in f if line.strip())

        # Apply the data-efficiency subset mask (e.g. only 5% of images)
        if split_file is not None:
            indices = np.load(split_file)
            all_ids = [all_ids[i] for i in indices]

        # Build (image_path, annotation_path) record for each image
        self.samples = []
        for img_id in all_ids:
            img_path = os.path.join(img_dir, f'{img_id}.jpg')
            xml_path = os.path.join(ann_dir, f'{img_id}.xml')
            if not os.path.exists(img_path):
                continue
            ann_path = xml_path if os.path.exists(xml_path) else None
            self.samples.append((img_path, ann_path))

    def __getitem__(self, i):
        img_path, ann_path = self.samples[i]
        image = Image.open(img_path).convert('RGB')

        if ann_path is not None:
            boxes, labels = _parse_annotation(ann_path)   # returns 0-indexed labels
        else:
            boxes  = np.zeros((0, 4), dtype=np.float32)
            labels = np.zeros((0,),   dtype=np.int64)

        boxes  = torch.FloatTensor(boxes)
        labels = torch.LongTensor(labels) + 1          # KEY: shift 0-19 → 1-20
        difficulties = torch.zeros(labels.size(0), dtype=torch.uint8)  # no difficulty in DIOR

        image, boxes, labels, difficulties = transform(
            image, boxes, labels, difficulties, split=self.split_name
        )
        return image, boxes, labels, difficulties
```

#### Key differences explained

| Aspect | Before (VOC) | After (DIOR) |
|--------|-------------|-------------|
| Input source | JSON files (pre-generated) | XML files (read directly) |
| Subset selection | Not supported — one fixed split | `split_file` param accepts any `.npy` |
| Label indexing | Already 1-indexed in JSON | 0-indexed from XML → **+1 shift applied** |
| Difficulty flag | Real values from VOC XML | All zeros (DIOR has no difficulty tag) |
| Image size | Varies (VOC is not uniform) | 800×800 → resized to 300×300 by `transform()` |
| Preprocessing step | `create_data_lists.py` must run first | None — reads annotations on the fly |

#### The label shift in detail

`dior_dataset.py` (from `Python_datareader/`) assigns class indices 0–19:

```
airplane → 0,  airport → 1,  ...,  windmill → 19
```

The SSD300 model reserves index 0 for **background**. In `MultiBoxLoss`,
any prior box with `true_class == 0` is treated as background and excluded
from the localization loss. If we passed 0-indexed labels directly, the model
would confuse `airplane` with `background`.

The fix is a single line:

```python
labels = torch.LongTensor(labels) + 1   # 0-19 → 1-20
```

This matches the layout in `utils.py` where `label_map['airplane'] = 1`.

## What Has NOT Changed

- **`model.py` (partial)** — The SSD300 prior boxes, NMS, `AuxiliaryConvolutions`,
  `PredictionConvolutions`, and `MultiBoxLoss` are all unchanged. The backbone
  has been replaced (VGGBase → ResNetBase) — see section 7 for details.

- **`utils.py` transforms** — `transform()`, `expand()`, `random_crop()`,
  `flip()`, `resize()`, and `photometric_distort()` all work on PIL images
  and coordinate tensors, so they apply to DIOR images without modification.
  The resize to 300×300 inside `transform()` handles the 800×800 → 300×300
  conversion automatically.

- **`MultiBoxLoss`** — Works on raw tensors. The only assumption it makes is
  that class index 0 = background, which our +1 shift satisfies.

### 4. `eval.py` — Evaluation

#### What it does

`eval.py` loads a trained checkpoint and measures detection quality using mAP.

#### Why the test split

The DIOR **test set** (11,738 images, IDs 11726–23463) **does have annotation
XML files** in the same `Annotations/Horizontal Bounding Boxes/` folder as the
trainval images. This makes it a proper held-out evaluation set.

For the final comparison table we evaluate SSD300 on the full test set (11,738
images) rather than the val split. This is a stronger and fairer holdout —
the val split was used by YOLO during training for early stopping and
hyperparameter decisions, so it is not a clean holdout. The val split is still
available as a loader option in `eval.py` if a direct epoch-by-epoch comparison
with YOLO's logged val metrics is needed.

- The best checkpoint is always preserved regardless of when training stops

### 7. `model.py` — Backbone: VGG16 → ResNet50 (pretrained ImageNet)

#### What changed

The `VGGBase` class (280 lines of manually defined VGG16 convolutions plus a
custom FC→conv decimation routine) has been replaced with a new `ResNetBase`
class that loads ResNet50 from `torchvision.models` and extracts two feature
maps from its intermediate layers.

`AuxiliaryConvolutions`, `PredictionConvolutions`, `MultiBoxLoss`, and
`SSD300.forward` are **completely unchanged** because ResNet50's layer2 and
layer3 outputs happen to produce the same channel dimensions as VGG (512 and
1024 respectively).

---

#### Why replace VGG16?

VGG16 was the backbone used in the original 2016 SSD paper. It was the best
publicly available architecture at the time, but by modern standards it has
serious weaknesses:

| Problem | Detail |
|---------|--------|
| No batch normalization | VGG was designed before BN became standard. Its activations vary wildly in scale across layers, which is why SSD needed an explicit L2-norm + learnable rescale layer (`rescale_factors`) on conv4_3. |
| Extremely wide first layers | VGG uses 64, 128, 256, 512, 512 channel counts across five blocks — very parameter-heavy. Most of the memory is in the fully-connected classifier layers (fc6, fc7) which SSD converts to atrous convolutions via a "decimation" trick. |
| No residual connections | Training is slower and gradients decay more across depth. Fine-tuning is harder when the network is not well-initialized. |
| Slow to fine-tune on new domains | Satellite imagery (overhead views, small objects, unusual aspect ratios) looks nothing like ImageNet street photos. VGG adapts slowly because its flat sequential structure gives no shortcut paths for gradient flow. |
| Deprecated API | `torchvision.models.vgg16(pretrained=True)` now raises a deprecation warning. The pretrained weight loading in VGGBase relies on manually copying and decimating FC weights — brittle code that breaks if the VGG16 architecture in torchvision ever changes. |

---

#### Why ResNet50 specifically? (Not ResNet18 or ResNet34)

All ResNets share the same block structure, but they differ in depth and
feature quality. Here is a direct comparison across the variants most
commonly considered:

| Property | ResNet18 | ResNet34 | **ResNet50** | ResNet101 |
|----------|----------|----------|-------------|-----------|
| Depth (layers) | 18 | 34 | **50** | 101 |
| Block type | Basic | Basic | **Bottleneck** | Bottleneck |
| ImageNet top-1 acc. | ~69.8% | ~73.3% | **~76.1%** | ~77.4% |
| Parameters | 11.7 M | 21.8 M | **25.6 M** | 44.5 M |
| layer2 channels | 128 | 128 | **512** | 512 |
| layer3 channels | 256 | 256 | **1024** | 1024 |
| Residual shortcuts | ✓ | ✓ | ✓ | ✓ |
| Bottleneck blocks | ✗ | ✗ | **✓** | ✓ |

**Why ResNet18 and ResNet34 are ruled out:**

ResNet18 and ResNet34 use the *Basic block* (two plain 3×3 convolutions per
block). Their intermediate channel counts are:

```
ResNet18/34:  layer2 → 128 ch,  layer3 → 256 ch
```

The SSD prediction heads (`PredictionConvolutions`) and auxiliary convolutions
(`AuxiliaryConvolutions`) are hard-wired to 512ch and 1024ch inputs — the
same sizes VGG16 produced. Using ResNet18/34 would require rebuilding those
layers with different channel sizes, which multiplies the number of changes and
risks introducing bugs.

ResNet50 uses the *Bottleneck block* (1×1 → 3×3 → 1×1 convolutions). Its
channel counts are:

```
ResNet50:  layer2 → 512 ch,  layer3 → 1024 ch
```

These are **identical** to VGG16's conv4_3 (512) and conv7 (1024). This means
the backbone is a true drop-in replacement: zero changes to AuxiliaryConvolutions,
zero changes to PredictionConvolutions, zero changes to SSD300.forward, and the
8,732 prior boxes are unchanged.

**Why not ResNet101 or deeper?**

ResNet101 and ResNet152 are more accurate on ImageNet (+1–2%) but the marginal
gain does not justify the cost for this study:

- ResNet101 has 44.5M parameters vs 25.6M for ResNet50 — nearly 2× heavier.
  With a batch size of 8 on a single GPU, ResNet101 significantly increases
  memory pressure and slows training.
- The DIOR dataset is satellite imagery. The domain gap between ImageNet (natural
  photos) and DIOR (overhead 800×800 images) means that deeper ImageNet features
  do not always transfer better. ResNet50 strikes the right balance between
  representation quality and fine-tuning flexibility.
- For a data efficiency study on small splits (5%, 25%), a lighter backbone
  actually generalizes better — deeper networks are more prone to overfitting
  when there are only ~600 training images.

**Summary of the choice:**

> ResNet50 is the smallest ResNet variant whose intermediate channel dimensions
> (512, 1024) are compatible with the existing SSD300 head. It is also the
> sweet spot between accuracy and compute cost, and the most widely used
> ResNet variant in object detection literature (Faster R-CNN, Mask R-CNN,
> and many SSD variants all default to ResNet50).

#### Before (`VGGBase`)

```python
class VGGBase(nn.Module):
    def __init__(self):
        super(VGGBase, self).__init__()

        # ~16 hand-defined Conv2d + MaxPool2d layers
        self.conv1_1 = nn.Conv2d(3, 64, kernel_size=3, padding=1)
        self.conv1_2 = nn.Conv2d(64, 64, kernel_size=3, padding=1)
        self.pool1   = nn.MaxPool2d(kernel_size=2, stride=2)
        # ... (conv2 through conv7, pool1 through pool5) ...

        # FC6 and FC7 converted to atrous convolutions
        self.conv6 = nn.Conv2d(512, 1024, kernel_size=3, padding=6, dilation=6)
        self.conv7 = nn.Conv2d(1024, 1024, kernel_size=1)

        self.load_pretrained_layers()   # manually decimates VGG16 fc weights

    def load_pretrained_layers(self):
        # Loads VGG16 conv weights directly
```

```python
    layer3 output → (N, 1024, 19, 19)  replaces conv7

        self.layer2 = backbone.layer2   # (N, 512, 38, 38) — feature map 1

        return conv4_3_feats, conv7_feats
```

### 8. `train.py` — Differential Learning Rate (backbone vs head)

#### What changed

The optimizer now uses **four parameter groups** instead of two. The pretrained
ResNet50 backbone receives a learning rate 10× lower than the randomly
initialised detection head.

---

#### Why this matters

When we switched from VGG16 (trained from scratch in the original code) to a
pretrained ResNet50, the learning rate strategy needed to change too. Here is
the core problem with a flat LR across all parameters:

**Epoch 1, batch 1 with LR = 1e-3 on the backbone:**
The backbone weights were carefully shaped over millions of ImageNet iterations
to recognise edges, textures, and object parts. A single gradient update at
1e-3 on randomly-matched DIOR targets can shift those weights far from their
ImageNet optimum — before the head has learned anything meaningful to guide
them. This is called **catastrophic forgetting**: the pretrained knowledge is
overwritten before it can be used.

The standard remedy is **differential learning rates** (sometimes called
"discriminative fine-tuning"):
- Backbone: low LR → weights move slowly, preserving ImageNet features
- Head: full LR → weights move fast, learning DIOR-specific detection logic

After a few epochs the head stabilises and the backbone can be gently pulled
toward the new domain without losing its general feature extraction ability.

---

#### Why 0.1× specifically?

The scale factor of 0.1 (giving backbone LR = 1e-4) is the most common choice
in fine-tuning literature for detection models:

| Scale | Backbone LR | Effect |
|-------|-------------|--------|
| 0.01× | 1e-5 | Almost frozen — safe but slow to adapt to satellite imagery |
| **0.1×** | **1e-4** | **Gentle adaptation — standard choice for detection fine-tuning** |
| 1.0× | 1e-3 | Same as head — catastrophic forgetting risk |

DIOR is satellite/overhead imagery which is quite different from ImageNet
(top-down views, small objects, very different textures). We want the backbone
to adapt, just slowly. `0.1×` strikes the right balance.

---

#### Why do biases still get 2× LR?

This comes from the original SSD paper. Biases converge more slowly than
weights because they are single scalars (no spatial structure to average
gradients over). Doubling their LR compensates. We preserve this rule within
each group, so the four groups are:

| Group | Parameters | LR |
|-------|-----------|-----|
| `backbone_biases` | `model.base` — bias terms | `2 × 1e-3 × 0.1 = 2e-4` |
| `backbone_params` | `model.base` — weight tensors | `1e-3 × 0.1 = 1e-4` |
| `head_biases` | `aux_convs`, `pred_convs`, `rescale_factors` — biases | `2 × 1e-3 = 2e-3` |
| `head_params` | `aux_convs`, `pred_convs`, `rescale_factors` — weights | `1e-3` |

When the fixed LR decay fires at epochs 150 and 180 (`adjust_learning_rate`
multiplies all groups by 0.1), the 10× backbone-to-head ratio is preserved
throughout training:

```
After epoch 150 decay (×0.1):
  backbone weights: 1e-4 → 1e-5
  head weights:     1e-3 → 1e-4

After epoch 180 decay (×0.1):
  backbone weights: 1e-5 → 1e-6
  head weights:     1e-4 → 1e-5
```

---

#### Before

```python
# Single flat split: bias vs non-bias, same LR ratio for backbone and head
biases, not_biases = [], []
for name, param in model.named_parameters():
    if param.requires_grad:
        (biases if name.endswith('.bias') else not_biases).append(param)

optimizer = torch.optim.SGD(
    [{'params': biases,     'lr': 2 * LR},   # ALL biases:  2e-3
     {'params': not_biases, 'lr':     LR}],   # ALL weights: 1e-3
    lr=LR, momentum=MOMENTUM, weight_decay=WEIGHT_DECAY,
)
```

Problem: pretrained backbone biases get `2e-3`, pretrained backbone weights
get `1e-3` — same as randomly initialised head. The ImageNet features get
overwritten in the first few epochs.

#### After

```python
BACKBONE_LR_SCALE = 0.1   # pretrained ResNet50 backbone gets 10× lower LR

backbone_params, backbone_biases = [], []
head_params,     head_biases     = [], []

for name, param in model.named_parameters():
    if not param.requires_grad:
        continue
    is_backbone = name.startswith('base.')   # ResNetBase is model.base
    is_bias     = name.endswith('.bias')
    if   is_backbone and is_bias:  backbone_biases.append(param)
    elif is_backbone:              backbone_params.append(param)
    elif is_bias:                  head_biases.append(param)
    else:                          head_params.append(param)

optimizer = torch.optim.SGD([
    {'params': backbone_biases, 'lr': 2 * LR * BACKBONE_LR_SCALE},  # 2e-4
    {'params': backbone_params, 'lr':     LR * BACKBONE_LR_SCALE},  # 1e-4
    {'params': head_biases,     'lr': 2 * LR},                       # 2e-3
    {'params': head_params,     'lr':     LR},                        # 1e-3
], momentum=MOMENTUM, weight_decay=WEIGHT_DECAY)
```

How `name.startswith('base.')` works: PyTorch names parameters by their
module path. `model.base` is the `ResNetBase` instance, so all of its
parameters are prefixed `base.stem.*`, `base.layer1.*`, `base.layer2.*`,
`base.layer3.*`. Everything else (`aux_convs.*`, `pred_convs.*`,
`rescale_factors`) is the head.

The CSV `lr` column now logs `optimizer.param_groups[3]['lr']` (head weights)
as the reference LR, since that is the "full" rate the head is training at.

### 11. `model.py` — Remove L2 norm and `rescale_factors` from `SSD300`

#### What changed

Two things were removed from `SSD300`:

1. `self.rescale_factors` — a learnable `(1, 512, 1, 1)` parameter initialised to 20
2. The three-line L2 norm block in `forward()` that used it

---

#### Why it existed for VGG

The original SSD paper noted that `conv4_3` activations (from VGG) had
**dramatically larger magnitudes** than the deeper feature maps fed into the
auxiliary convolutions. VGG has no batch normalization anywhere — activations
accumulate unchecked across 13 convolutional layers. The fix was:

```
1. Compute per-spatial-location L2 norm across the 512 channels
2. Divide by that norm  →  every location becomes a unit vector
3. Multiply by a learnable per-channel scale (init=20)  →  bring magnitude back
```

This was a **VGG-specific patch** for an **unnormalized feature map**. It
appears exactly once in the architecture and only for `conv4_3`.

---

#### Why it is wrong for ResNet50

ResNet50 uses BatchNorm after every convolutional layer inside each bottleneck
block. The structure of one bottleneck is:

```
Conv 1×1 → BN → ReLU
Conv 3×3 → BN → ReLU
Conv 1×1 → BN
+ residual shortcut
→ ReLU
```

By the time data exits `layer2` (38×38), it has passed through **4 bottleneck
blocks**, each normalizing its output. The activations are already
approximately zero-mean, unit-variance per channel (before the learned
gamma/beta parameters inside BN). Applying L2 norm on top causes three
concrete problems:

| Problem | Detail |
|---------|--------|
| Destroys spatial magnitude information | L2 norm forces every spatial location to unit length. Features that are large because they strongly respond to an object become identical in magnitude to features that weakly respond. The prediction head loses a useful signal. |
| `rescale_factors` init=20 destabilizes early training | After L2 norm, features are unit vectors. Multiplying by 20 before the head has learned anything sends gradients back through the prediction head at 20× the natural scale, causing large, noisy weight updates in the first few epochs — the opposite of the stable fine-tuning we want. |
| Wasted parameter budget | `rescale_factors` has 512 parameters. During training they would converge toward small values to undo the amplification. Those 512 parameters and their gradient computation add cost without benefit. |

---

#### Before

```python
# SSD300.__init__
self.rescale_factors = nn.Parameter(torch.FloatTensor(1, 512, 1, 1))
nn.init.constant_(self.rescale_factors, 20)

# SSD300.forward
conv4_3_feats, conv7_feats = self.base(image)

norm = conv4_3_feats.pow(2).sum(dim=1, keepdim=True).sqrt()  # (N, 1, 38, 38)
conv4_3_feats = conv4_3_feats / norm                          # (N, 512, 38, 38)
conv4_3_feats = conv4_3_feats * self.rescale_factors          # (N, 512, 38, 38)
```

#### After

```python
# SSD300.__init__
# (rescale_factors removed entirely)

# SSD300.forward
conv4_3_feats, conv7_feats = self.base(image)  # BN already normalizes — no extra step needed
```

The 38×38 feature map flows directly from `ResNetBase.layer2` into
`PredictionConvolutions` with no modification. BatchNorm inside ResNet50
handles all the normalization that L2 norm was patching around.

### 12. `model.py` — Weight initialization: Xavier uniform → Kaiming normal

#### What changed

Both `AuxiliaryConvolutions.init_conv2d()` and
`PredictionConvolutions.init_conv2d()` had their weight initialization
changed from Xavier uniform to Kaiming normal. Biases remain zero.

#### Before (both classes)

```python
def init_conv2d(self):
    for c in self.children():
        if isinstance(c, nn.Conv2d):
            nn.init.xavier_uniform_(c.weight)
            nn.init.constant_(c.bias, 0.)
```

#### After (both classes)

```python
def init_conv2d(self):
    for c in self.children():
        if isinstance(c, nn.Conv2d):
            nn.init.kaiming_normal_(c.weight, mode='fan_out', nonlinearity='relu')
            nn.init.constant_(c.bias, 0.)
```

---

#### Why Xavier is wrong for ReLU networks

Xavier initialization (Glorot & Bengio, 2010) derives the correct variance
for weight tensors by assuming the activation function has a **linear region
around zero** — it was designed for `tanh` and `sigmoid`. The derivation
ensures that the variance of activations and gradients stays roughly constant
as you go deeper through the network.

The key assumption Xavier makes is that the activation function preserves
variance symmetrically. The formula it produces is:

```
Var(W) = 2 / (fan_in + fan_out)
```

ReLU breaks this assumption. ReLU sets all negative activations to exactly
zero — it kills roughly **half the neurons** on every forward pass. This
means the effective variance of the output is halved compared to what Xavier
predicts. If you stack multiple ReLU layers with Xavier init, variance shrinks
by ~0.5× per layer, causing gradients to vanish in deeper networks.

---

#### Why Kaiming (He) is correct for ReLU networks

He et al. (2015) — the same paper that introduced ResNets — derived an
initialization specifically for ReLU. They accounted for the half-zeroing
by doubling the variance:

```
Var(W) = 2 / fan_in          (mode='fan_out' uses fan_out in the denominator)
```

The factor of 2 exactly compensates for the ~50% of neurons ReLU kills,
keeping activation variance stable across layers.

**`mode='fan_out'`** — uses the number of output connections (filters ×
kernel_h × kernel_w) as the denominator. This is preferred for convolutional
layers where the gradient flows back through `fan_out` connections. It
stabilizes the **backward pass**, which is especially important for the
prediction head since gradients must flow cleanly back through these layers
into the backbone during fine-tuning.

**`nonlinearity='relu'`** — tells PyTorch to use the gain factor of
`sqrt(2)` appropriate for ReLU (as opposed to `leaky_relu`, `tanh`, etc.).

---

#### Does this affect the backbone?

No. `ResNetBase` loads pretrained ImageNet weights — its initialization is
fixed by torchvision and `init_conv2d` is never called on it. Only the two
randomly-initialized modules are affected:

| Module | Layers initialized | Init before | Init after |
|--------|--------------------|-------------|------------|
| `AuxiliaryConvolutions` | conv8_1, conv8_2, conv9_1, conv9_2, conv10_1, conv10_2, conv11_1, conv11_2 | Xavier uniform | Kaiming normal |
| `PredictionConvolutions` | 6 loc convs + 6 cls convs | Xavier uniform | Kaiming normal |
| `ResNetBase` | All ResNet50 layers | — | pretrained ImageNet (unchanged) |

### 13. `model.py` — Fix deprecated `reduce=False` in `MultiBoxLoss`

#### What changed

One argument in the `CrossEntropyLoss` constructor was updated:

```python
# Before
self.cross_entropy = nn.CrossEntropyLoss(reduce=False)

# After
self.cross_entropy = nn.CrossEntropyLoss(reduction='none')
```

---

#### Why `reduce=False` is dangerous

PyTorch replaced the `reduce` argument with `reduction` in version 1.0 (2018).
The old argument was kept for a while with a deprecation warning, but in newer
PyTorch versions it is **silently ignored**.

To understand why silent ignoring is catastrophic here, you need to know what
this loss is supposed to return and how it is used immediately after.

**What `reduction='none'` does:**

`CrossEntropyLoss` normally computes one loss value per sample and then
averages or sums them into a single scalar. `reduction='none'` tells it to
return **every individual loss value** as a separate number — no collapsing.

In `MultiBoxLoss.forward()`, the loss is called like this:

```python
conf_loss_all = self.cross_entropy(
    predicted_scores.view(-1, n_classes),   # shape: (N × 8732, 21)
    true_classes.view(-1)                   # shape: (N × 8732,)
)
# Expected output shape: (N × 8732,)  — one loss per prior box
conf_loss_all = conf_loss_all.view(batch_size, n_priors)  # reshape to (N, 8732)
```

The code needs `conf_loss_all` to be shape `(N × 8732,)` so it can:
1. Reshape it to `(N, 8732)` — one loss per image per prior box
2. Zero out the positive priors (they are handled separately)
3. Sort the remaining negatives by loss to find the hardest ones (Hard Negative Mining)
4. Select the top `3 × n_positives` hardest negatives per image

**What happens if `reduce=False` is silently ignored:**

If PyTorch ignores `reduce=False` and falls back to the default
`reduction='mean'`, the loss returns a **single scalar** instead of
`(N × 8732,)` values. The very next line:

```python
conf_loss_all = conf_loss_all.view(batch_size, n_priors)  # tries to reshape scalar to (N, 8732)
```

...crashes with a `RuntimeError: shape mismatch` on the **first batch of
epoch 1**. Training never starts.

The fix is one word: `reduce=False` → `reduction='none'`.

### 14. `model.py` — Fix deprecated `torch.uint8` boolean tensor in NMS

#### What changed

Three related lines inside `detect_objects()` were updated together. You
cannot change one without the others — they form a single logical unit.

```python
# Before — uint8 dtype, arithmetic negation
suppress = torch.zeros((n_above_min_score), dtype=torch.uint8).to(device)
...
image_boxes.append(class_decoded_locs[1 - suppress])
image_labels.append(torch.LongTensor((1 - suppress).sum().item() * [c]).to(device))
image_scores.append(class_scores[1 - suppress])

# After — bool dtype, logical NOT operator
suppress = torch.zeros((n_above_min_score), dtype=torch.bool).to(device)
...
image_boxes.append(class_decoded_locs[~suppress])
image_labels.append(torch.LongTensor((~suppress).sum().item() * [c]).to(device))
image_scores.append(class_scores[~suppress])
```

---

#### Understanding the NMS loop and what `suppress` does

Non-Maximum Suppression (NMS) removes duplicate detections. After sorting all
boxes for a class by confidence score (highest first), the algorithm works
like this:

```
For each box in descending score order:
    If this box is already marked for suppression → skip it
    Otherwise → suppress every other box that overlaps this one by > 45%
                 (keep this box itself — it is the winner)
```

`suppress` is a 1D tensor, one entry per candidate box. It tracks which boxes
have been eliminated:

- `False` (or 0) = keep this box
- `True`  (or 1) = suppress this box

At the end of the loop, we want to **select the boxes that were NOT
suppressed** — i.e., the surviving detections.

---

#### Why `torch.uint8` was used originally

In early PyTorch (before 1.2), there was no `torch.bool` type. Boolean
operations returned `torch.uint8` (unsigned 8-bit integer) tensors where
`0 = False` and `1 = True`. This was the standard way to do masking.

Arithmetic negation `1 - suppress` worked because:
- `1 - 0 = 1` → keep (was not suppressed)
- `1 - 1 = 0` → remove (was suppressed)

So `class_decoded_locs[1 - suppress]` selected only the non-suppressed boxes.

---

#### Why `torch.uint8` is now problematic

PyTorch introduced `torch.bool` in version 1.2 and deprecated `uint8` for
boolean operations. In newer versions:

**Problem A — `torch.max` mixing dtypes:**

Inside the NMS loop there is this line:

```python
suppress = torch.max(suppress, overlap[box] > max_overlap)
```

`overlap[box] > max_overlap` returns a `torch.bool` tensor (modern PyTorch).
`suppress` is `torch.uint8`. Taking `torch.max` between a `uint8` tensor and
a `bool` tensor causes a dtype mismatch warning and can produce incorrect
results in some PyTorch versions, because `uint8` and `bool` have different
internal representations even though their values look the same.

**Problem B — `1 - suppress` is not boolean NOT:**

`1 - uint8_tensor` worked as a boolean flip only because the values were
guaranteed to be 0 or 1. But `uint8` can hold values 0–255. If any bug
or dtype promotion ever put a value other than 0 or 1 into `suppress`, the
arithmetic would silently produce wrong selections without any error.

---

#### Why `torch.bool` + `~` is the correct fix

`torch.bool` is PyTorch's proper boolean type. It can only hold `True` or
`False` — there is no ambiguity. The `~` operator is the **logical NOT** for
boolean tensors:

```python
~False  →  True   (box was not suppressed → keep it)
~True   →  False  (box was suppressed → remove it)
```

This replaces the `1 - suppress` arithmetic with the semantically correct
boolean operation. It also makes the intent of the code immediately clear to
anyone reading it — you are performing a logical negation, not subtraction.

**Why all three lines must change together:**

| Line | Why it must change |
|------|--------------------|
| `dtype=torch.uint8` | Creates the suppress tensor — must be `torch.bool` so `~` works and `torch.max` receives matching types |
| `class_decoded_locs[1 - suppress]` | Selects kept boxes — `1 - bool` is undefined; must be `[~suppress]` |
| `(1 - suppress).sum().item()` | Counts kept boxes to build the label list — must be `(~suppress).sum().item()` |
| `class_scores[1 - suppress]` | Selects kept scores — must be `[~suppress]` |

Changing `dtype` without changing the three indexing lines would make
`1 - suppress` produce an integer tensor (not bool), breaking indexing in
newer PyTorch. All four lines are a single atomic fix.

```python
for m in self.modules():
    if isinstance(m, nn.BatchNorm2d):
        for p in m.parameters():
            p.requires_grad_(False)

# New method added to ResNetBase:
def train(self, mode=True):
    super(ResNetBase, self).train(mode)
    for m in self.modules():
        if isinstance(m, nn.BatchNorm2d):
            m.eval()
    return self
```

---

#### Background: what is inside a BatchNorm layer?

A `nn.BatchNorm2d` layer holds four things, and it is critical to understand
which category each falls into:

| Name | Type | What it is | Updated by |
|------|------|-----------|-----------|
| `weight` (γ) | Learnable parameter | Per-channel scale | Optimizer (backprop) |
| `bias` (β) | Learnable parameter | Per-channel shift | Optimizer (backprop) |
| `running_mean` | Buffer | Long-run average of batch means | Automatic, every forward pass in train mode |
| `running_var` | Buffer | Long-run average of batch variances | Automatic, every forward pass in train mode |

**Parameters** (γ, β) are controlled by the optimizer — you can exclude them
by setting `requires_grad=False`.

**Buffers** (`running_mean`, `running_var`) are NOT parameters. They have no
gradients. The optimizer never touches them. They update automatically during
every forward pass as long as the BN layer is in **training mode**:

```
running_mean = (1 - momentum) * running_mean + momentum * batch_mean
running_var  = (1 - momentum) * running_var  + momentum * batch_var
```

PyTorch's default BN momentum is `0.1`, meaning each new batch contributes
10% to the running estimate.

---

#### The corruption problem with BATCH_SIZE = 8

ResNet50 was pretrained on ImageNet using batch sizes of 256 or larger. The
`running_mean` and `running_var` inside every BN layer were built from
thousands of batches of 256 diverse images — they are accurate, stable
estimates of what the activations look like across the whole ImageNet
distribution.

When we fine-tune with `BATCH_SIZE = 8` on DIOR:

- Each batch contains 8 overhead satellite images
- The batch mean and variance computed from 8 images are **noisy** — they
  jump around significantly from batch to batch because the sample is tiny
- With momentum=0.1, after just **22 batches** the pretrained running stats
  have lost half their influence: `(1 - 0.1)^22 ≈ 0.5`
- After a full epoch on the 5% split (~75 batches), the pretrained stats are
  almost entirely replaced with noisy DIOR estimates

This means:
1. The stable, accurate ImageNet statistics that made the pretrained features
   good are destroyed within the first epoch
2. Each forward pass during training uses unreliable batch statistics, causing
   the activations to fluctuate — the backbone features become unstable
3. During evaluation (when BN switches to running stats), the corrupted stats
   produce different activations than during training — the model sees a
   different input distribution at eval time than it trained on

This is a form of catastrophic forgetting that happens through the buffer
path, completely bypassing the differential LR protection we added for the
conv weights.

---

#### Why `requires_grad_(False)` alone is not enough

You might think: "just freeze γ and β with `requires_grad=False`, and the BN
is frozen." This is **wrong** — it only freezes the learnable affine
parameters. The running stats are buffers, not parameters. They continue
updating every forward pass regardless of `requires_grad`.

Conversely, calling `m.eval()` alone in `__init__` is **also not enough**:

```python
# This does NOT work
def __init__(self):
    ...
    for m in self.modules():
        if isinstance(m, nn.BatchNorm2d):
            m.eval()   # sets mode to eval — good
```

Our training loop calls `model.train()` at the top of every epoch inside
`train_one_epoch()`. `model.train()` recursively calls `.train()` on every
submodule, which flips all BN layers back to training mode. The one-time
`m.eval()` call in `__init__` is immediately undone on the first training
epoch.

A complete freeze requires **both**:

| What | How | What it freezes |
|------|-----|----------------|
| `p.requires_grad_(False)` on BN params | In `__init__` | γ and β — excluded from optimizer |
| Override `train()` to call `m.eval()` | New method | `running_mean` and `running_var` — never update |

---

#### How the `train()` override works

PyTorch's `model.train()` works by recursively calling `.train(mode)` on
every child module. The call chain for our model looks like:

```
SSD300.train()
  └── ResNetBase.train()      ← our override intercepts here
        └── stem.train()
        └── layer1.train()
        └── ...
              └── BatchNorm2d.train()   ← would switch to train mode
```

Our override intercepts at the `ResNetBase` level:

```python
def train(self, mode=True):
    super(ResNetBase, self).train(mode)   # step 1: let PyTorch do its normal thing
                                          # (all BN layers now in train mode)
    for m in self.modules():
        if isinstance(m, nn.BatchNorm2d):
            m.eval()                      # step 2: immediately flip every BN back
    return self                           # (running stats now frozen)
```

Step 1 runs the standard recursive `.train()` on all submodules — including
the BN layers, which switch to train mode. Step 2 immediately overrides that
for BN specifically, forcing them back to eval mode. The net result: every
call to `model.train()` from the training loop ends with backbone BN in eval
mode. The running stats never update.

---

#### How `requires_grad_(False)` integrates with our optimizer

In `train.py`, the optimizer construction already skips frozen parameters:

```python
for name, param in model.named_parameters():
    if not param.requires_grad:   # ← this filter catches BN gamma/beta
        continue
    is_backbone = name.startswith('base.')
    ...
```

Because `requires_grad_(False)` was called on all BN parameters in
`ResNetBase.__init__`, those parameters are invisible to the optimizer loop —
no extra change needed in `train.py`. The four optimizer groups (backbone
weights, backbone biases, head weights, head biases) are built correctly
without any BN parameters included.

---

#### What stays unfrozen

Only the backbone BN layers are frozen. The rest of the model trains normally:

| Component | BN layers | Conv/Linear weights | Status |
|-----------|-----------|---------------------|--------|
| `ResNetBase` (backbone) | Frozen — eval mode, γ/β excluded from optimizer | Trainable at 0.1× LR | Partially frozen |
| `AuxiliaryConvolutions` | None (no BN) | Trainable at full LR | Fully trainable |
| `PredictionConvolutions` | None (no BN) | Trainable at full LR | Fully trainable |

The head layers (`AuxiliaryConvolutions`, `PredictionConvolutions`) have no
BatchNorm at all — they were randomly initialised and train from scratch.
This is correct: those layers need to fully adapt to DIOR.

---

#### Impact on results

This fix is most impactful on:

- **Small splits (5%, 25%)** — fewer batches per epoch means the corruption
  accumulates faster relative to the number of learning steps. Freezing BN
  preserves the pretrained feature quality that makes transfer learning
  valuable when data is scarce.
- **Evaluation stability** — with frozen running stats, the model sees
  identical activation distributions at train and eval time. Without the fix,
  the train/eval distribution mismatch would cause val mAP to be an
  unreliable signal, making early stopping decisions noisier.

### 16. `train.py` + `eval.py` — Switch to `state_dict` checkpoints (PyTorch 2.6+ fix)

#### What changed

Three things were updated in `train.py`, and one in `eval.py`:

1. A new `_build_optimizer(model)` helper was extracted
2. `_save()` now stores `model.state_dict()` and `optimizer.state_dict()` instead of the full objects
3. The resume block reconstructs model and optimizer from scratch before loading the state dicts
4. All `torch.load()` calls now pass `weights_only=True` explicitly

---

#### Why the old approach breaks on PyTorch 2.6+

The original code pickled entire Python objects:

```python
# Old _save()
torch.save({
    'model'    : model,       # entire nn.Module object
    'optimizer': optimizer,   # entire SGD object
    ...
}, path)

# Old load
ckpt      = torch.load(path, map_location=device)
model     = ckpt['model']       # unpickle nn.Module
optimizer = ckpt['optimizer']   # unpickle SGD
```

Pickling an `nn.Module` serialises the entire Python class — its code,
attributes, and all tensor weights — into a binary stream. Loading it back
requires **executing arbitrary Python code** embedded in the pickle stream.

PyTorch 2.6 (January 2025) changed `torch.load()` to default to
`weights_only=True`. Under this mode, PyTorch only deserialises safe types
(tensors, basic scalars, lists, dicts). Loading a pickled `nn.Module` or
optimizer object is blocked and raises:

```
_pickle.UnpicklingError: Weights only load failed.
```

The server running training is on **PyTorch 2.8.0** — well past the 2.6
threshold. With the old code, any attempt to resume a crashed run would
fail immediately on the `torch.load()` call, losing all progress for that
split.

---

#### The state_dict approach

A `state_dict` is simply an `OrderedDict` mapping parameter names to their
tensors. It contains no Python code, no class definitions, no executable
logic — just the numbers. This is what `weights_only=True` is designed to
load safely.

```python
# state_dict contains only this kind of data:
{
    'base.stem.0.weight': tensor(...),   # conv1 weights
    'base.layer1.0.bn1.weight': tensor(...),
    ...
    'pred_convs.loc_conv4_3.weight': tensor(...),
}
```

The optimizer's state dict is similarly a plain dict of scalars and momentum
tensors — no Python objects, safe to load with `weights_only=True`.

---

#### The reconstruction requirement

The downside of state dicts is that you cannot load weights into nothing —
you need a model instance first, then pour the weights into it. This is why
the resume path now has two steps instead of one:

```python
# Old resume — one step, load the whole object
model = ckpt['model']

# New resume — two steps: reconstruct, then load weights
model = SSD300(n_classes=n_classes)       # step 1: build empty model
model.load_state_dict(ckpt['model'])      # step 2: fill in the weights
```

Same for the optimizer:

```python
# Old resume
optimizer = ckpt['optimizer']

# New resume
optimizer = _build_optimizer(model)           # step 1: build optimizer structure
optimizer.load_state_dict(ckpt['optimizer'])  # step 2: restore LR state, momentum buffers
```

The optimizer must be built with `_build_optimizer()` first because
`load_state_dict()` only restores the **values** (learning rates, momentum
buffers) — it does not reconstruct the parameter groups. If the structure
does not match, PyTorch raises a `ValueError`.

---

#### Why `_build_optimizer` was extracted into a helper

Before this change, the 4-group parameter splitting code lived only inside
the `else` branch (fresh start). The resume branch needed the same logic.
Duplicating 15 lines of parameter grouping would be a maintenance hazard —
if we ever change the LR groups, we'd have to update two places in sync.

Extracting it into `_build_optimizer(model)` means both paths call one
function:

```python
# Fresh start
model     = SSD300(n_classes=n_classes)
optimizer = _build_optimizer(model)

# Resume
model     = SSD300(n_classes=n_classes)
model.load_state_dict(ckpt['model'])
optimizer = _build_optimizer(model)
optimizer.load_state_dict(ckpt['optimizer'])
```

---

#### Before and after

**`_save()` — before:**
```python
def _save(path, epoch, model, optimizer, best_mAP, no_improve):
    torch.save({
        'epoch'     : epoch,
        'model'     : model,           # ← full nn.Module object (breaks PyTorch 2.6+)
        'optimizer' : optimizer,       # ← full SGD object (breaks PyTorch 2.6+)
        'best_mAP'  : best_mAP,

```

**`_save()` — after:**
```python

    torch.save({
        'epoch'     : epoch,
        'model'     : model.state_dict(),      # ← safe: only tensors
        'optimizer' : optimizer.state_dict(),  # ← safe: only scalars + tensors
        'best_mAP'  : best_mAP,
        'no_improve': no_improve,
    }, path)
```

**Resume block — before:**
```python
ckpt      = torch.load(latest_path, map_location=device)
model     = ckpt['model']
optimizer = ckpt['optimizer']
```

**Resume block — after:**
```python
ckpt      = torch.load(latest_path, map_location=device, weights_only=True)
model     = SSD300(n_classes=n_classes)
model.load_state_dict(ckpt['model'])
optimizer = _build_optimizer(model)
optimizer.load_state_dict(ckpt['optimizer'])
```

**`eval.py` — before:**
```python
checkpoint = torch.load(checkpoint_path, map_location=device)
model      = checkpoint['model']
```

**`eval.py` — after:**
```python
checkpoint = torch.load(checkpoint_path, map_location=device, weights_only=True)
model      = SSD300(n_classes=len(label_map))
model.load_state_dict(checkpoint['model'])
```

### 17. `model.py` — Fix localization loss: plain L1 → Smooth L1 (Huber)

#### What changed

One word in `MultiBoxLoss.__init__()`:

```python
# Before — plain L1, despite the variable name and comment saying otherwise
self.smooth_l1 = nn.L1Loss()  # *smooth* L1 loss in the paper

# After — actual Smooth L1 as the SSD paper specifies
self.smooth_l1 = nn.SmoothL1Loss()
```

---

#### What the original code actually had

The variable was named `smooth_l1` and the comment explicitly said
"*smooth* L1 loss in the paper" — but the loss object was `nn.L1Loss()`,
which is plain L1. This was a bug inherited from the original tutorial,
where the author acknowledged in the comment that they were using the wrong
loss and left it anyway.

---

#### The difference between plain L1 and Smooth L1

Both losses measure the distance between the predicted box offset and the
true box offset. The difference is in how they treat small vs large errors:

**Plain L1:**
```
L(x) = |x|
```
Gradient is always ±1, regardless of how big or small the error is.

**Smooth L1 (Huber loss, β=1 in PyTorch's default):**
```
L(x) = 0.5 × x²        if |x| < 1   (quadratic region)
L(x) = |x| - 0.5       if |x| ≥ 1   (linear region)
```
Gradient is `x` for small errors (proportional) and ±1 for large errors (capped).

Visually:

```
Loss
 |         /  Plain L1
 |        /
 |       /-------- Smooth L1
 |      /  ↑quadratic
 |_____/
 0     1        |error|
```

---

#### Why this matters for SSD training

SSD training has two very different phases:

**Early training — large localization errors:**
Box predictions start far from the ground truth. Both L1 and Smooth L1
behave identically here (both are linear, gradient = ±1). No difference.

**Later training — small localization errors (converging):**
This is where plain L1 causes problems. When the predicted box is close to
the target (error < 1 pixel in normalized coordinates), plain L1 still
applies a gradient of ±1. This is too aggressive for fine adjustments —
the optimizer overshoots, the loss oscillates around the minimum instead
of settling, and final box precision suffers.

Smooth L1 switches to a quadratic (gradient proportional to the error)
when the error is small. The gradient shrinks as the prediction gets
closer to the target, allowing the model to make fine, stable adjustments
in the final stages of convergence.

**Differentiability:**
Plain L1 has a non-differentiable kink at zero — the gradient is undefined
at the minimum. Smooth L1 is differentiable everywhere, which means the
optimizer always has a well-defined gradient signal, even at near-perfect
predictions.

---

#### Why the SSD paper used Smooth L1

The original SSD paper (Liu et al., 2016) explicitly states the localization
loss uses Smooth L1, citing Faster R-CNN (Girshick, 2015) which introduced
it for exactly this reason: detection models see highly variable error
magnitudes during training — huge errors early on, tiny errors late — and
Smooth L1 handles both regimes correctly by being linear for large errors
(robust, like L1) and quadratic for small errors (precise, like L2).

---

#### Impact on our training

The fix is most noticeable in:

- **Final box precision** — predicted boxes will converge more tightly to
  ground truth because the loss does not oscillate near the minimum
- **Training stability** — the smooth gradient transition prevents the
  localization loss from spiking when predictions are almost correct
- **Small splits (5%, 25%)** — with fewer training images, every gradient
  signal matters more; the noisy ±1 gradient from plain L1 near convergence
  wastes optimization steps

### 18. `datasets.py` + `train.py` + `generate_splits.py` — Fix data leakage: val images inside training pool

#### The bug

This was the most critical correctness issue in the entire pipeline. Tracing
the data flow exposed it:

**`generate_splits.py` (old):**
```python
train_ids = read_ids('train.txt')   # 5,862 images
val_ids   = read_ids('val.txt')     # 5,863 images
all_ids   = train_ids + val_ids     # 11,725 images — FULL trainval pool
```

The `.npy` index files were built against this 11,725-image pool. A stratified
shuffle mixed train.txt and val.txt images together before cutting the nested
slices — meaning every split contained roughly 50% val.txt images.

**`datasets.py` (old):**
```python
if split == 'trainval':
    id_files = ['train.txt', 'val.txt']   # training pool = train + val
```

**`train.py` (old):**
```python
train_dataset = DIORDataset(split='trainval', split_file=split_file, ...)
val_dataset   = DIORDataset(split='val',      split_file=None, ...)
```

The training pool and the validation set shared images. The exact overlap
at each split was:

| Split | Training images | Val images inside training | Overlap % |
|-------|----------------|---------------------------|-----------|
| split_005 | ~586 | ~293 | ~50% of val in training |
| split_025 | ~2,931 | ~1,466 | ~50% of val in training |
| split_050 | ~5,862 | ~2,932 | ~50% of val in training |
| split_075 | ~8,793 | ~4,397 | ~50% of val in training |
| split_100 | 11,725 | **5,863** | **100% of val in training** |

---

#### Why this corrupts the entire training pipeline

**1. Val mAP is an optimistic lie:**
Every 10 epochs, `compute_val_mAP()` runs on the val set. With leaked
images, the model has already trained on a large fraction of those images.
The reported val mAP measures performance on training data — not
generalisation. It will be inflated.

**2. Best checkpoint is selected on the wrong signal:**
`best_ssd300.pth.tar` is saved whenever val mAP improves. With a leaked
val set, "best val mAP" means "best fit to training data" — which is
exactly the overfitting signal the val set was supposed to catch. The
saved checkpoint is optimised for training, not for unseen images.

**3. Early stopping fires on the wrong signal:**
Early stopping increments `no_improve` when val mAP stops improving. With
leaked images, the model can keep improving its "val" score simply by
continuing to overfit the training data. Early stopping becomes unreliable
— it either fires too late (model is overfitting but val score still
rises) or too early (model converged on generalisation but keeps overfitting
leaked images).

**4. The SSD vs YOLO comparison is unfair:**
YOLOv8n was trained on `train.txt` only (~5,862 images at split_100) with
`val.txt` as a clean held-out validation set. The old SSD setup trained on
11,725 images at split_100 — double the data — while pretending val was a
clean holdout. The learning curves would be measuring different things.

---

#### The fix — three files changed

**`generate_splits.py` — change the pool to `train.txt` only:**

```python
# OLD — data leakage
train_ids = read_ids('train.txt')
val_ids   = read_ids('val.txt')

```

The `.npy` files were regenerated. All indices now fall in `[0, 5861]`
— exclusively within `train.txt`. Verified:

```
split_005: 293  indices, max=5847   ← within train.txt (0–5861) ✓
split_025: 1465 indices, max=5860   ✓
split_050: 2931 indices, max=5860   ✓
split_075: 4396 indices, max=5861   ✓
split_100: 5862 indices, max=5861   ✓
```

**`datasets.py` — replace `split='trainval'` with `split='train'`:**

```python

if split == 'trainval':
    id_files = ['train.txt', 'val.txt']   # ← read both, val images enter pool

# NEW

    id_files = ['train.txt']              # ← train.txt only, val.txt never loaded
```

```
val.txt     5,863 images  ← held-out validation (checkpoint selection, early stopping)
test.txt   11,738 images  ← final evaluation only (never seen during training)
```

Three non-overlapping sets. The comparison with YOLOv8n is now symmetric:

### 19. `utils.py` — Fix `is` vs `==` string comparison in `photometric_distort`

#### What changed

One character in `photometric_distort()`:

```python
# Before — identity comparison (wrong)
if d.__name__ is 'adjust_hue':

# After — equality comparison (correct)
if d.__name__ == 'adjust_hue':
```

---

#### Why `is` is wrong here

Python has two ways to compare things:

- `==` — **value equality**: are the contents the same?
- `is` — **identity**: are these the exact same object in memory?

For string comparisons, you almost always want `==`. Using `is` on strings
relies on a CPython implementation detail called **string interning** — where
the interpreter caches and reuses identical short string objects to save
memory. Because `'adjust_hue'` is a short, simple string, CPython often
interns it, meaning `d.__name__ is 'adjust_hue'` accidentally evaluates
`True` most of the time.

But "most of the time" is not "always". The Python language specification
does **not** guarantee that any particular string will be interned. The
behaviour depends on:
- Which Python implementation you're using (CPython vs PyPy)
- Which version (interning rules changed between versions)
- Whether the string was created at compile time or at runtime
- Whether it contains only alphanumeric characters and underscores

`d.__name__` is the `__name__` attribute of a `torchvision.transforms.functional`
function object — its exact interning behaviour depends on how torchvision
constructs it internally. Under the wrong conditions, `is` returns `False`
even though the names are identical, and the `adjust_factor` for hue is
never set.

**What happens when it silently fails:**

The code then falls into the `else` branch:
```python
adjust_factor = random.uniform(0.5, 1.5)   # wrong range for hue
new_image = FT.adjust_hue(new_image, adjust_factor)  # hue called with 0.5–1.5 instead of ±18/255
```

`FT.adjust_hue` expects a factor in `[-0.5, 0.5]`. Passing `0.5–1.5` either
clamps silently or raises a ValueError depending on the torchvision version.
Either way, hue augmentation is broken without any error message.

**Python 3.8+ makes this explicit:** comparing a variable to a string literal
using `is` now emits:
```
SyntaxWarning: "is" with a literal. Did you mean "=="?
```

The fix is one character: `is` → `==`.

### 20. `datasets.py` — Unify duplicate label definitions (single source of truth)

#### What changed

`DIOR_CLASSES` in `datasets.py` was a hardcoded list that duplicated
`dior_labels` from `utils.py`. It is now imported from `utils.py` instead:

```python
# Before — two independent definitions that must be kept in sync manually
# In utils.py:
dior_labels = (
    'airplane', 'airport', 'baseballfield', 'basketballcourt', 'bridge',
    'chimney', 'dam', 'Expressway-Service-area', 'Expressway-toll-station',
    'golffield', 'groundtrackfield', 'harbor', 'overpass', 'ship', 'stadium',
    'storagetank', 'tenniscourt', 'trainstation', 'vehicle', 'windmill',
)

# In datasets.py:
DIOR_CLASSES = [
    "airplane", "airport", "baseballfield", "basketballcourt", "bridge",
    "chimney", "dam", "Expressway-Service-area", "Expressway-toll-station",
    "golffield", "groundtrackfield", "harbor", "overpass", "ship", "stadium",
    "storagetank", "tenniscourt", "trainstation", "vehicle", "windmill",
]
DIOR_CLASS_TO_IDX = {c: i for i, c in enumerate(DIOR_CLASSES)}

# After — single source of truth
# In datasets.py:
from utils import transform, dior_labels

DIOR_CLASSES      = list(dior_labels)
DIOR_CLASS_TO_IDX = {c: i for i, c in enumerate(DIOR_CLASSES)}
```

---

#### Why duplicate definitions are dangerous

`datasets.py` uses `DIOR_CLASS_TO_IDX` to parse XML annotations into
0-indexed class integers (0–19). `utils.py` uses `dior_labels` to build
`label_map`, which maps class names to 1-indexed SSD integers (1–20). The
`+1` shift in `__getitem__` bridges them:

```
XML name → DIOR_CLASS_TO_IDX → 0-indexed → +1 → 1-indexed → label_map
```

This chain only works if both lists are in **identical order**. When they
were two independent hardcoded lists, a future edit to one (renaming a class,
reordering, adding a new one for a different dataset variant) would silently
corrupt the label mapping for every class that shifted position — no error,
just wrong class IDs assigned to all annotations, and the model would train
on mislabelled data.

With one import, editing `dior_labels` in `utils.py` automatically updates
`DIOR_CLASS_TO_IDX` in `datasets.py`. The chain cannot drift.

### 21. `datasets.py` — Filter empty-annotation images at construction time

#### What changed

`DIORDataset.__init__()` now parses each annotation during dataset
construction and skips images that have zero valid objects. `__getitem__()`
is simplified because `ann_path` is now guaranteed to be a valid XML with
at least one object.

---

#### The crash path

Before the fix, two locations in the code assumed every image has at least
one object:

**Location 1 — `random_crop` in `utils.py`:**
```python
overlap = find_jaccard_overlap(...)   # shape: (n_objects, n_candidates)
current_overlap = overlap.max().item()   # crashes if n_objects == 0
```
`max()` on an empty tensor raises `RuntimeError: max() arg is an empty sequence`.

**Location 2 — `MultiBoxLoss.forward` in `model.py`:**
```python
overlap = find_jaccard_overlap(boxes[i], self.priors_xy)  # (n_objects, 8732)
overlap_for_each_prior, object_for_each_prior = overlap.max(dim=0)  # crashes if n_objects == 0
```
`max(dim=0)` on a `(0, 8732)` tensor raises `RuntimeError: Expected reduction
dim 0 to have non-zero size`.

Neither location has error handling. If a single empty-annotation image
lands in a training batch, the entire training run crashes mid-epoch — after
potentially hours of GPU time on the larger splits.

---

#### How an empty-annotation image can appear

`_parse_annotation` returns an empty `(0, 4)` array in two situations:

1. **The XML file does not exist** — previously the code set `ann_path = None`
   and `__getitem__` created empty tensors, which then crashed downstream.

2. **All `<object>` entries fail the class-name match** — if any XML contains
   only object names not in `DIOR_CLASS_TO_IDX`, every object is silently
   skipped via `continue`, leaving an empty array.

DIOR is a clean, well-annotated dataset so neither case fires in practice.
But "does not fire in practice" is not the same as "cannot fire" — a
corrupted XML, a partially-written file from an interrupted download, or a
dataset variant with slightly different class names would trigger it silently.
The crash would happen mid-training, not at startup.

---

#### Before

```python
# __init__ — includes images regardless of annotation content
self.samples = []
for img_id in all_ids:
    img_path = os.path.join(img_dir, f'{img_id}.jpg')
    xml_path = os.path.join(ann_dir, f'{img_id}.xml')
    if not os.path.exists(img_path):
        continue
    ann_path = xml_path if os.path.exists(xml_path) else None
    self.samples.append((img_path, ann_path))   # ann_path may be None

# __getitem__ — had to guard against None ann_path
if ann_path is not None:
    boxes, labels = _parse_annotation(ann_path)
else:
    boxes  = np.zeros((0, 4), dtype=np.float32)   # empty → crash downstream
    labels = np.zeros((0,),   dtype=np.int64)
```

#### After

```python
# __init__ — eagerly filter empty-annotation images
self.samples = []
skipped = 0
for img_id in all_ids:
    img_path = os.path.join(img_dir, f'{img_id}.jpg')
    xml_path = os.path.join(ann_dir, f'{img_id}.xml')
    if not os.path.exists(img_path):
        continue
    if not os.path.exists(xml_path):       # no annotation file → skip
        skipped += 1
        continue
    boxes, _ = _parse_annotation(xml_path)
    if len(boxes) == 0:                    # annotation exists but no valid objects → skip
        skipped += 1
        continue
    self.samples.append((img_path, xml_path))   # guaranteed ≥ 1 object
if skipped:
    print(f'  [{split}] Skipped {skipped} images with no annotated objects.')

# __getitem__ — no None-check needed, ann_path always valid
boxes, labels = _parse_annotation(ann_path)
```

**Why filter at construction time rather than in `__getitem__`:**

`__getitem__` cannot "skip" an item — the DataLoader calls it by index and
expects a result. The only options are to raise an exception (crashes the
run) or return dummy data (silently corrupts the batch). Filtering at
`__init__` removes bad images from the index entirely before training starts.
The cost is a few seconds of annotation parsing at startup — negligible
compared to GPU hours of training.

### 22. `train.py` — Replace val mAP early stopping with conf_loss plateau detection

#### What changed

Early stopping was originally based on val mAP@0.5 computed every `EVAL_EVERY=10`
epochs over the full 5,863-image val set. This was replaced with a conf_loss
plateau check that runs every epoch with no extra forward pass cost.

---

#### Before

```python
EVAL_EVERY = 10
PATIENCE   = 10   # eval checks, not epochs → 100 epochs without improvement

# Inside training loop:
is_eval_epoch = ((epoch + 1) % EVAL_EVERY == 0) or (epoch == MAX_EPOCHS - 1)
if is_eval_epoch:
    val_mAP = compute_val_mAP(model, val_loader)   # iterate all 5,863 val images
    if val_mAP > best_mAP:
        best_mAP   = val_mAP
        no_improve = 0
        _save(best_path, ...)
    else:
        no_improve += 1
if no_improve >= PATIENCE:
    break   # stop after 10 bad eval checks = 100 epochs
```

#### After

```python
PATIENCE  = 20      # consecutive epochs without conf_loss improvement
MIN_DELTA = 0.001   # minimum improvement that counts as progress

# Inside training loop — runs every epoch, no val loop:
if conf_loss < best_conf_loss - MIN_DELTA:
    best_conf_loss = conf_loss
    no_improve     = 0
    _save(best_path, ...)
else:
    no_improve += 1
if no_improve >= PATIENCE:
    break   # stop after 20 consecutive epochs with no meaningful improvement
```

---

#### Why this change was made

**The val mAP loop was the bottleneck.** Running `calculate_mAP` over 5,863
val images requires a full inference pass (forward + NMS + IoU matching for
all 8,732 priors × all val images × all 20 classes). On a single GPU this
takes several minutes per eval check. With `EVAL_EVERY=10` that means 20 eval
runs over 200 epochs — significant wall-clock overhead that slows down the
entire 5-split experiment.

**Why conf_loss is a valid proxy for convergence:**

`conf_loss` is the hard-negative-mined cross-entropy loss over all 8,732
prior boxes. It measures how confidently and correctly the model assigns class
labels to anchor boxes — which is exactly what mAP captures at evaluation
time. When conf_loss plateaus, the model has stopped learning to distinguish
object classes from background, which is the primary signal that training has
converged.

`loc_loss` (box regression) is not used as the stopping signal because it
typically converges faster than classification and can plateau early even when
the model is still learning to classify correctly.

**Why MIN_DELTA = 0.001:**

Raw conf_loss values are typically in the range 1–3 after initial training.
An improvement of 0.001 is ~0.03–0.1% of the loss magnitude — small enough
that anything below it is numerical noise rather than genuine learning.

**Why PATIENCE = 20 epochs:**

- The two LR decay steps at epoch 150 and 180 can temporarily spike or
  stagnate conf_loss as the optimizer adjusts to the new learning rate. A
  patience of 20 epochs gives the model enough time to recover from these
  bumps before early stopping fires.
- For split_005 (293 images, 37 batches/epoch), 20 epochs is ~740 gradient
  steps — enough to confirm a genuine plateau rather than a transient stall.
- For split_100 (5,862 images, 733 batches/epoch), 20 epochs is ~14,660
  gradient steps — still a reasonable window.

**Trade-off acknowledged:**

conf_loss plateau is a training-set signal, not a generalisation signal. It
can stop training when the model is still improving on unseen data (underfitting
risk) or continue training past the generalisation peak (overfitting risk on
small splits). Val mAP would give a cleaner stopping criterion. For this study
the speed gain outweighs the imprecision, and final mAP is measured by
`eval.py` on the held-out test set regardless of when training stopped.

### 23. `eval.py` — CUDA out of memory during NMS: raise MIN_SCORE and lower TOP_K

#### What changed

Two constants at the top of `eval.py` were adjusted:

```python
# Before
MIN_SCORE = 0.01
TOP_K     = 200

# After
MIN_SCORE = 0.05
TOP_K     = 100
```

---

#### Why the OOM happened

The crash occurred inside `find_jaccard_overlap` called from `model.detect_objects` during Non-Maximum Suppression (NMS), not during the model's forward pass. The error was:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 358.00 MiB.
```

For each class, NMS takes every box that passed the confidence threshold and computes IoU between every box and every other box. If there are N boxes above the threshold, this produces an **N × N** matrix:

```python
overlap = find_jaccard_overlap(class_decoded_locs, class_decoded_locs)  # (N, N)
```

With `MIN_SCORE = 0.01`, almost every prior box passes the filter — the model outputs 8,732 prior boxes per image, and at 1% confidence hundreds of low-confidence boxes survive per class. With `BATCH_SIZE = 8`, the NMS matrix across one batch becomes enormous and the allocation fails.

The server GPU (7.60 GiB total) also had two other processes running simultaneously (2.24 GiB + 954 MB), leaving only 128 MB free — making an already tight situation impossible.

---

#### Why raising MIN_SCORE fixes it

`MIN_SCORE = 0.05` means only boxes where the model is at least 5% confident survive into NMS. In practice this cuts the candidate count from hundreds per class down to tens, making the N × N matrix orders of magnitude smaller.

**Does this affect mAP?**

Barely. mAP is computed by sweeping a precision-recall curve across all confidence thresholds. Boxes with confidence 0.01–0.05 contribute only to the extreme low-precision end of the PR curve — a region where recall is near 1.0 but precision is near 0. The area under the curve in that region is negligible. In practice the difference between `MIN_SCORE=0.01` and `MIN_SCORE=0.05` is typically **< 0.1% mAP**.

`TOP_K = 100` caps the number of boxes entering NMS per class at 100 (down from 200). This only affects images where the model detects more than 100 instances of a single class, which does not occur in DIOR.

| Change | Effect on mAP | Effect on memory |
|--------|--------------|-----------------|
| `MIN_SCORE 0.01 → 0.05` | < 0.1% | Cuts N in N×N NMS matrix significantly |
| `TOP_K 200 → 100` | Negligible | Additional cap on N |
| `BATCH_SIZE 8 → 4` (optional) | Zero | Halves per-batch GPU pressure |

The experiment integrity is fully preserved. These are engineering parameters that control GPU memory use during post-processing, not scientific parameters that determine what the model learned.

### 24. `utils.py` — Fix device mismatch in `calculate_mAP` (CPU tensor indexed by GPU mask)

#### What changed

One line in `calculate_mAP()`:

```python
# Before — torch.LongTensor creates a CPU tensor
original_ind = torch.LongTensor(range(true_class_boxes.size(0)))[true_class_images == this_image][ind]

# After — .to(device) moves it to the same device as the mask
original_ind = torch.LongTensor(range(true_class_boxes.size(0))).to(device)[true_class_images == this_image][ind]
```

---

#### Why this crashes

The error was:

```
RuntimeError: indices should be either on cpu or on the same device as the indexed tensor (cpu)
```

**`true_class_images == this_image` is a GPU tensor.**

`true_labels` is populated in `eval.py`'s inference loop:

```python
labels = [l.to(device) for l in labels]   # moved to GPU
true_labels.extend(labels)
```

Everything that flows through `true_labels` ends up on GPU. Inside `calculate_mAP`, `true_class_images` is derived from the same GPU tensors. The boolean mask `true_class_images == this_image` is therefore a **GPU tensor**.

**`torch.LongTensor(range(...))` is always a CPU tensor.**

`torch.LongTensor` without specifying a device always allocates on CPU. This is a PyTorch design choice — the plain constructor never inherits a current device.

**PyTorch cannot index a CPU tensor with a GPU mask.**

When you write `cpu_tensor[gpu_mask]`, PyTorch requires both to be on the same device. Since they are not, it raises the RuntimeError.

---

#### Why this was never caught before

The original `calculate_mAP` was written for Pascal VOC where ground-truth tensors were kept on CPU throughout evaluation. In our adapted `eval.py`, boxes and labels are moved to GPU (lines 99–101) for speed during the 35-minute inference run over 11,738 test images. This created a device mismatch the original code was never designed to handle.

---

#### The full context of what this line does

Inside the TP/FP matching loop of `calculate_mAP`, for each detected box we find which ground-truth box it matched with, then mark that GT box as "already detected" to prevent double-counting:

```python
# Step 1: find all GT boxes in this image for this class
object_boxes = true_class_boxes[true_class_images == this_image]

# Step 2: compute IoU between the detection and each GT box
overlaps = find_jaccard_overlap(this_detection_box, object_boxes)
max_overlap, ind = torch.max(overlaps.squeeze(0), dim=0)   # ind = local index in image

# Step 3: convert local index → global index in true_class_boxes
original_ind = torch.LongTensor(range(true_class_boxes.size(0))).to(device)[true_class_images == this_image][ind]
#              ^-- range over ALL GT boxes of this class            ^-- filter to this image    ^-- pick matched one

# Step 4: mark as detected to prevent double-counting
true_class_boxes_detected[original_ind] = 1
```

The `.to(device)` moves the index range tensor to GPU before the mask is applied. Without it, step 3 crashes. With it, all tensors are on the same device and the lookup succeeds.
